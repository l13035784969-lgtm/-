# 旅游行程规划 App —— 架构设计文档

> 定位：**行程规划类**旅游应用（对标 Wanderlog / 马蜂窝"行程"功能）
> 平台：**微信小程序 / H5 优先**，预留跨端到 App 的能力
> 状态：v0.1（首个架构草案，供评审与迭代）

---

## 1. 产品定位与核心场景

### 1.1 一句话定位
帮助用户"规划一次旅行"：从目的地灵感 → 行程编排 → 行程后回顾分享，形成闭环。（出行中导航打卡为二期能力）

### 1.2 核心用户旅程（MVP 必须覆盖）
1. 创建行程：选目的地 + 日期范围，生成一个"行程"容器
2. 添加行程项：按天添加地点（景点/餐厅/酒店），支持地图搜索 POI
3. 排序与时间安排：拖拽调整每天顺序，设置到达/停留时间
4. 行程分享：生成图文行程卡片，分享给好友或朋友圈

### 1.3 二期功能（不进 MVP，架构需预留扩展点）
- **地图总览**：查看整个行程在地图上的路线与分布（暂缓）
- **出行中导航/打卡**：当天行程一键导航、拍照+定位签到打卡（暂缓）
- AI 行程推荐 / 智能填充
- 协作编辑（多人共同规划一个行程）
- 内容社区（公开行程广场、他人行程一键复制）
- 预订能力接入（酒店/门票，接第三方 OTA）
- 离线地图与弱网可用性

> 说明：地图/POI 搜索能力在 MVP 中仍会用到（用于"添加行程项"时搜索地点），但**行程地图总览**和**出行中导航打卡**两项暂不在首个版本实现，待核心行程编辑与分享跑通后再评估。

## 2. 技术选型

### 2.1 前端（小程序 / H5）

| 项 | 选型 | 理由 |
|---|---|---|
| 框架 | **Taro（React 语法）** | 一套代码同时出微信小程序 + H5，未来可平滑扩展到 App（Taro + RN） |
| 状态管理 | Zustand / Redux Toolkit | 行程编辑状态较复杂（多层嵌套：行程→天→项），需要可预测的状态管理 |
| 地图 SDK | 微信小程序内置 `<map>` 组件 + **腾讯位置服务（地图 SDK / WebService API）** | 小程序官方推荐地图服务商，POI 搜索、逆地理编码、路线规划齐全，且小程序内免额外授权成本 |
| UI 组件库 | Taro UI 或 NutUI | 覆盖小程序常见组件，减少自研成本 |

> **为什么不做纯原生小程序**：Taro 牺牲的性能损耗对行程规划类（非重度动画/游戏）应用可忽略，换来的跨端能力和 React 生态值得。

### 2.2 后端

| 项 | 选型 | 理由 |
|---|---|---|
| 语言/框架 | **Node.js + NestJS**（或团队更熟悉的 Go + Gin） | 与前端同语言栈（TS），团队协作成本低；NestJS 的模块化天然贴合"用户/行程/POI/媒体"的领域划分 |
| 架构风格 | **模块化单体（Modular Monolith）** | MVP 阶段不上微服务，按领域模块划分代码，保留未来拆分的边界 |
| 数据库 | **PostgreSQL** | 行程数据强关系（用户-行程-天-行程项），事务一致性重要 |
| 地理查询 | PostgreSQL + **PostGIS** 扩展 | 若未来做"附近推荐/公开行程地理检索"，PostGIS 原生支持地理索引 |
| 缓存 | Redis | 会话、POI 搜索结果缓存、限流 |
| 对象存储 | 腾讯云 COS / 阿里云 OSS | 行程封面图、分享卡片图（打卡照片存储为二期需求） |
| 消息/异步任务 | BullMQ（基于 Redis） | 图片压缩、行程卡片生成等异步处理 |

### 2.3 关键第三方服务

| 能力 | 服务商 | 说明 |
|---|---|---|
| 地图与 POI | 腾讯位置服务 | 小程序场景下官方合规首选；国内覆盖度高 |
| 登录 | 微信小程序登录（`wx.login` + openid/unionid） | 免用户自建密码体系 |
| 消息推送 | 微信订阅消息 | 行程当天提醒 |
| 内容安全 | 微信内容安全 API（`msgSecCheck` / `imgSecCheck`） | 行程标题/封面图等 UGC 内容过审，合规要求（打卡内容审核为二期需求） |
| 分享 | 微信原生转发 + 服务端生成分享卡片图（Canvas/SSR） | 行程卡片分享到朋友圈 |

## 3. 系统架构

```
┌──────────────────────┐
│  微信小程序 / H5(Taro)  │
└───────────┬───────────┘
            │ HTTPS (小程序需走微信备案域名)
            ▼
┌──────────────────────┐
│      API 网关/BFF      │  ← 鉴权、限流、聚合裁剪响应
└───────────┬───────────┘
            ▼
┌───────────────────────────────────────────┐
│         后端服务（NestJS 模块化单体）           │
│  ┌────────┐ ┌────────┐ ┌────────┐ ┌──────┐ │
│  │ 用户模块 │ │ 行程模块 │ │ POI模块 │ │媒体模块│ │
│  └────────┘ └────────┘ └────────┘ └──────┘ │
└──────┬───────────────┬──────────────┬───────┘
       ▼               ▼              ▼
  PostgreSQL         Redis        对象存储(COS)
  (+PostGIS)       (缓存/队列)      (图片/卡片)
            │
            ▼
   第三方服务：腾讯位置服务 / 微信开放能力
```

**设计原则**：
- MVP 阶段坚持单体，避免过早微服务化带来的运维复杂度
- 模块间通过明确的 Service 接口调用，禁止跨模块直接操作对方数据表 —— 为未来拆分预留边界
- BFF 层做好裁剪聚合，减少小程序端的多次请求（首屏行程详情一次性返回天+行程项+POI 信息）

## 4. 核心数据模型（概要 ER）

```
User (用户)
 ├─ id, openid, unionid, nickname, avatar_url, created_at

Trip (行程)
 ├─ id, owner_id(FK User), title, cover_image, start_date, end_date,
 │  destination, status(draft/published), created_at

TripDay (行程日)
 ├─ id, trip_id(FK Trip), date, day_index

TripItem (行程项/一天中的一个安排)
 ├─ id, trip_day_id(FK TripDay), poi_id(FK POI, nullable),
 │  title, start_time, duration_minutes, sort_order, note

POI (兴趣点，缓存腾讯位置服务返回的地点)
 ├─ id, external_id(第三方POI id), name, category,
 │  location(geography point), address

ShareCard (分享卡片，异步生成)
 ├─ id, trip_id, image_url, generated_at
```

> `CheckIn`（打卡记录，含定位签到）为二期实体，MVP 数据模型暂不建表，待出行中导航打卡功能启动时再设计。

## 5. 非功能性需求

| 维度 | 要求 | 落地方式 |
|---|---|---|
| **小程序合规** | 域名备案 + ICP 备案 + 后端需 HTTPS | 上线前预留 2-4 周备案周期，需提前启动 |
| **隐私/位置权限** | POI 搜索需明确授权提示（打卡定位为二期） | 遵循微信小程序隐私协议规范，明示位置用途 |
| **内容合规** | 行程标题/封面图涉及 UGC | 接入微信内容安全 API，异步审核 + 违规拦截 |
| **性能** | 小程序包体积限制（主包 2MB） | 分包加载，地图等非首屏功能放分包 |
| **可观测性** | 需知道行程创建转化率、崩溃率 | 接入小程序官方数据分析 + 自建埋点（关键路径：创建行程→添加行程项→分享） |

## 6. 项目目录结构建议

```
/
├── apps/
│   ├── miniapp/          # Taro 小程序/H5 前端
│   │   ├── src/
│   │   │   ├── pages/
│   │   │   ├── components/
│   │   │   ├── store/
│   │   │   └── services/ # API 调用封装
│   └── api/               # NestJS 后端
│       ├── src/
│       │   ├── modules/
│       │   │   ├── user/
│       │   │   ├── trip/
│       │   │   ├── poi/
│       │   │   └── media/
│       │   └── common/
├── docs/
│   └── architecture.md    # 本文档
└── README.md
```

采用 **Monorepo**（pnpm workspace）管理前后端，共享 TypeScript 类型定义（如 `Trip`、`TripItem` 接口），减少前后端字段不一致的问题。

## 7. 开发路线图

| 阶段 | 周期 | 交付 |
|---|---|---|
| 阶段 0：项目初始化 | 第 1 周 | Monorepo 骨架、CI、小程序空壳跑通登录 |
| 阶段 1：行程创建与编辑 | 第 2-4 周 | 创建行程、按天添加/排序行程项、POI 搜索 |
| 阶段 2：行程分享 | 第 5-6 周 | 生成图文分享卡片、微信转发 |
| 阶段 3：内测与打磨 | 第 7-8 周 | 埋点上线、邀请种子用户、修复体验问题 |
| 阶段 4（二期）：地图总览与出行打卡 | 待评估 | 行程地图总览、导航跳转、拍照打卡 |

## 8. 开放问题（需产品/业务决策）

1. 是否需要游客模式（不登录可浏览示例行程）？
2. 打卡照片是否需要长期保留 / 是否有存储成本上限？
3. 是否要在 MVP 就做"公开行程广场"，还是完全私有？（影响是否要做内容审核链路）
4. 未来是否计划出 App（决定 Taro → RN 迁移的优先级）？
