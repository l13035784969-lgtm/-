# 旅游行程规划 App —— 架构设计文档

> 定位：**行程规划类**旅游应用（对标 Wanderlog / 马蜂窝"行程"功能）
> 平台：**微信小程序 / H5 优先**，预留跨端到 App 的能力
> 状态：v0.1（首个架构草案，供评审与迭代）

---

## 1. 产品定位与核心场景

### 1.1 一句话定位
帮助用户"规划一次旅行"：从目的地灵感 → 行程编排 → 同行费用 AA → 行程后回顾分享，形成闭环，出行中单点导航也在 MVP 内。（拍照打卡签到为二期能力）

### 1.2 核心用户旅程（MVP 必须覆盖）
1. 创建行程：选目的地 + 日期范围，生成一个"行程"容器；**创建者自动加入为第一个 `TripMember`**（已确认，见下方说明），否则创建者自己没法记账、参与命运轮盘
2. 添加行程项：按天添加地点（景点/餐厅/交通/其他，见分类说明），用微信原生地点选择器搜索选点；**具体时间可以先不填**，之后再补（见 4 项说明）；每个行程项**已确认自带"导航"按钮**，点击调用 `wx.openLocation()` 跳转地图 App 指路——地点数据添加时就存了经纬度，这个按钮是零额外成本的顺手功能（技术选型见 2.1），不用等到二期
3. **添加住宿**：设置入住/退房日期和酒店，跨天展示（不占用某一天的时间轴，见 1.2.1）
4. 排序与时间安排：**拖拽定顺序是主要交互，时间是可选的辅助标注**（已确认）——`sort_order` 决定当天列表的先后，`start_time` 允许为空，不做时间冲突校验，保持最简单的心智模型
5. **费用记账与 AA 结算**：拉同行人加入行程，记录每一笔花费（谁付的、多少钱、谁分摊），自动计算每人应收/应付，给出最少转账笔数的结算方案；细化为"即时AA与垫付追踪"，见 1.2.2
6. **命运轮盘·冤大头模式**：决策僵局解不开时（去哪吃饭、去哪个景点），转盘随机抽一个人拥有本轮"独裁权"，其他人无条件跟从；细化见 1.2.3
7. 行程分享：生成图文行程卡片，分享给好友或朋友圈；**卡片内容尽量简单、点击"分享"那一刻才现场生成**（已确认，见下方说明）

> 说明：功能 5、6 都需要多人加入同一个行程才有意义，因此 MVP 需要引入轻量级的"**行程成员（TripMember）**"概念——仅用于邀请同行人加入行程、参与费用分摊/转盘抽签，**不等同于**"协作编辑行程内容"（后者仍是二期功能，见 1.3）。行程安排本身在 MVP 阶段仍由创建者一人编辑。
>
> **已确认**：创建 `Trip` 的同一个事务里，自动为创建者插入一条 `TripMember` 记录（`user_id` 就是创建者自己，非占位成员，不需要认领），否则创建者没法用记账和命运轮盘这两个需要 `TripMember` 身份的功能。

#### 1.2.0 添加行程项 / 排序的补充细节 —— 已确认

- **时间可以先不填**：`TripItem.start_time` 允许为空。不填时间的项目归入当天列表里的"待安排"分组，用户后续可以随时回来补时间，不强制一次性填完
- **`TripItem` 增加分类字段**：`category`（景点/餐厅/交通/其他），用于列表里区分图标和筛选，和 `Expense.category`（餐饮/交通/门票/住宿/其他）是两套独立的枚举，不复用——一个描述"这是什么地点"，一个描述"这笔钱花在哪类"，语义不同
- **拖拽排序与时间是两件独立的事，不做冲突校验**：`sort_order` 决定当天列表的先后顺序，靠拖拽调整；`start_time` 只是可选的辅助标注。就算用户把"晚饭"拖到"午饭"前面、两者的 `start_time` 数值上还是"晚饭"更晚，系统也不会报错或自动改时间——这是刻意选择的最简单方案，不引入时间冲突检测/自动重排的复杂度

#### 1.2.1 住宿为什么单独处理

景点/餐厅是"某一天的某个时间点访问一次"，而住宿是"从入住到退房横跨多天"，两者形态不同，不能用同一套数据结构：
- **不放进 `TripItem`**：`TripItem` 挂在单个 `TripDay` 上、按 `start_time + duration_minutes` 描述单点访问，硬塞入住宿会导致要么只在入住当天显示（其余几天看不到"今晚住哪"），要么被迫在每天重复添加
- **展现方式**：住宿信息在行程详情页里，以固定卡片展示在"入住日到退房日"覆盖的每一天（如每天顶部/底部的"今晚住 XX 酒店"），与当天景点/餐厅的时间轴列表分开；行程总览页也单独列一个"住宿"栏，一眼看到全程分几段分别住哪

#### 1.2.2 即时AA与垫付追踪（共享钱袋 + 快速记账 + 离团结算）

**a) 共享钱袋 —— 虚拟记账，不托管真实资金**

"预充值"只在数据库里记一个数字，钱不会真的转到平台账户；公共消费从这个虚拟余额里扣。这是刻意的取舍：如果做成真实资金托管（用户的钱真转进平台账户统一管理），在国内属于资金存管/类金融业务，需要支付牌照或挂靠持牌机构，合规成本对 MVP 来说过高。**已确认**：MVP 只做虚拟钱袋，用户实际转账仍靠下面的结算单人工完成。

**b) 快速文字记账（MVP 用文字替代语音，已确认）**

原方案是语音记账（说一句话自动记一笔），但语音识别 ASR 是按用量计费的第三方服务，且需要额外处理识别出错的兜底逻辑。**已确认**：MVP 改用文字快速记账——输入框支持简写格式（如"老王 打车 43"），前端/后端做轻量的文字解析（正则提取金额 + 模糊匹配垫付人到已加入的 `TripMember`），同样默认分摊全团，同样**生成待确认草稿，弹给用户看一眼再正式入账**（文字解析也可能匹配错人，确认这一步不能省）。语音记账整体移入 1.3 二期功能，不产生 ASR 调用费用。入口位置**已确认**为行程详情页顶部的常驻输入框，见 2.6。

**c) 离团结算**

本质是把某几笔 `Expense` 下某个成员的 `ExpenseSplit` 标记剔除，按剩余参与人数重新分摊金额，复用现有数据模型即可，不需要新实体，只需要一个"重算"操作。

**d) 转账明细的呈现形式 —— 已确认，有个真实的平台限制**

微信/支付宝**都不支持**第三方 App 生成一个链接、点击后自动跳转到转账页面并预填好金额和收款人（反诈骗监管下没有对私转账的深度链接开放给个人对个人场景）。所以"一键转账直达"做不到。**已确认方案**：结算页只生成清晰的结算单文案（如"你应转给老王 87.5 元"）+ 一个"复制金额"按钮，不放收款码，用户自己打开微信/支付宝手动转账。

**e) 占位成员账号绑定 —— 已确认**

创建者添加占位成员（比如输个"老王"，人还没扫码进小程序）时，系统为这条记录生成一个专属的"认领"入口（本质是一张带 `claim_token` 的小程序码/转发卡片），转发给老王。老王点击后：
- 已登录小程序 → 直接把 `user_id` 写入这条 `TripMember` 记录，`claim_token` 失效，之前记在"老王"名下的账自动变成他自己的
- 未登录 → 先走小程序登录，登录后自动完成认领

不用手机号这类敏感权限去做匹配，直接复用已有的登录能力和邀请码机制，实现成本最低，也不需要额外的隐私授权说明。

**f) 费用记录编辑权限 —— 已确认**

同行人本来就是熟人小团体，MVP 优先效率而不是严格权限管控：**任意 `TripMember` 都可以编辑/删除任意一条 `Expense`**（文字快速记账解析错了、别人代记的账算错了，谁看到都能随手改），不做"仅创建人能改"这类限制。为了不出现"改了却不知道谁改的"，`Expense` 记录最后一次修改人和时间（见 4 节 `updated_by`/`updated_at`），不做完整版本历史，保持简单。

#### 1.2.3 命运轮盘·冤大头模式

流程：有人在群里僵住了（去哪吃/去哪玩谁都不表态）→ 发起一轮转盘，输入本轮决策主题（自由文本，如"晚餐吃什么"）→ 选参与人（默认当前所有 `TripMember`，可取消勾选不参与的人）→ 转盘动画结束，展示"XX 本轮独裁，说了算"。

**结果必须由后端统一生成并落库，不能纯前端随机**——转盘的意义是"全团看到同一个结果"，如果每人手机各转各的用前端随机数，结果对不上、还可能被怀疑作弊；服务端抽签、落一条记录，所有人打开看到的是同一个结果。

**动画节奏 —— 已确认："转动几秒再停"，不是点一下瞬间出结果**。这条决定牵出一个实现顺序上的细节：既然结果必须由后端生成（上面这条），动画流程就不能是"前端先转、转完再上报后端"，而要反过来——**点击"开始"时先请求后端拿到确定的结果，再播放几秒的转盘动画，动画结束时刚好停在后端返回的那个人身上**。参与人头像/名字均匀分布在转盘上，转盘转动几圈后逐渐减速、定格。用户体验上感觉是"命运正在决定"，实际上结果在动画一开始就已经算好了，只是没有立刻甩出来。

**结果一旦生成即锁定，不可重抽**（除非发起人主动作废这一轮、重新开一轮新的）——这条限制是刻意加的：没有它，"命运轮盘"会退化成"抽到不满意就一直转到满意为止"，"愿赌服输"这个乐趣点就没了。

结果页附带一个"加入行程"快捷按钮，点击可以直接把这次的决策主题带入"添加行程项"表单（1.2 第2项），不强制，纯顺手。

**零额外成本**：不依赖地图、语音、支付等任何第三方付费服务，纯自建随机+落库逻辑；功能体量小，不单独拆模块，归入行程模块（trip module）实现即可。

#### 1.2.4 行程分享 —— 已确认

- **卡片内容尽量简单**：只放标题 + 封面图 + 日期范围（如"8月三亚之旅 · 8.1-8.5"），不放参与人头像、不放行程亮点摘要这类需要额外排版和维护的内容
- **点击"分享"那一刻才现场生成，不预先生成**：用户点分享按钮时，后端实时用 Canvas/SSR 渲染这张卡片图并返回，前端展示短暂的生成中状态。**这个决定顺带简化了架构**：不需要为分享卡片单独维护一张 `ShareCard` 数据表或走异步队列预生成，直接按需渲染+上传对象存储即可（见 4 节数据模型、2.2 技术选型的相应调整）

### 1.3 二期功能（不进 MVP，架构需预留扩展点）
- **地图总览**：查看整个行程在地图上的路线与分布（暂缓；需要后端调用腾讯位置服务做路线计算，届时才需要评估付费/商业授权问题，见 2.3、9）
- **拍照打卡签到**：到达行程项对应地点后拍照+定位签到，生成"到此一游"记录（暂缓；需要新建 `CheckIn` 数据表、处理照片上传存储、UGC 图片内容审核，是有实打实开发量和存储成本的部分）。**已确认拆分**：单纯"导航去这里"不属于这条，已挪入 MVP（见 1.2 第2项），因为复用免费的 `wx.openLocation` 和已有的选点经纬度数据，几乎零增量成本
- **语音记账**：说一句话自动识别金额/垫付人记一笔账（暂缓，MVP 用文字快速记账替代，见 1.2.2 b；语音识别 ASR 是按量计费的第三方服务，二期再评估投入）
- AI 行程推荐 / 智能填充
- 协作编辑（多人共同规划一个行程）
- 内容社区（公开行程广场、他人行程一键复制）
- 预订能力接入（酒店/门票，接第三方 OTA）
- 离线地图与弱网可用性

> 说明：地点选择能力在 MVP 中仍会用到（用于"添加行程项"时搜索地点），但改用微信原生 `wx.chooseLocation`（免费，见 2.1），不涉及自建 POI 搜索后端。单点"导航去这里"也在 MVP（`wx.openLocation`，免费）。暂不在首个版本实现的是**行程地图总览**（整趟行程画路线，需要后端地理计算）和**拍照打卡签到**（需要新数据表/存储/审核），这两项待核心行程编辑与分享跑通后再评估。

## 2. 技术选型

### 2.1 前端（小程序 / H5）

| 项 | 选型 | 理由 |
|---|---|---|
| 框架 | **Taro（React 语法）** | 一套代码同时出微信小程序 + H5，未来可平滑扩展到 App（Taro + RN） |
| 状态管理 | Zustand / Redux Toolkit | 行程编辑状态较复杂（多层嵌套：行程→天→项），需要可预测的状态管理 |
| 地点选择/导航 | 微信原生 `wx.chooseLocation()`（选点）+ `wx.openLocation()`（跳转地图导航） | **已确认**：均为微信官方免费原生 API，不需要申请腾讯位置服务开发者 Key，规避免费额度限制和商业授权费风险；代价是选点 UI 用微信官方样式，不能自定义搜索/筛选体验 |
| UI 组件库 | Taro UI 或 NutUI | 覆盖小程序常见组件，减少自研成本 |

> **为什么不做纯原生小程序**：Taro 牺牲的性能损耗对行程规划类（非重度动画/游戏）应用可忽略，换来的跨端能力和 React 生态值得。

### 2.2 后端

| 项 | 选型 | 理由 |
|---|---|---|
| 语言/框架 | **Node.js + NestJS**（或团队更熟悉的 Go + Gin） | 与前端同语言栈（TS），团队协作成本低；NestJS 的模块化天然贴合"用户/行程/POI/媒体/费用"的领域划分 |
| 架构风格 | **模块化单体（Modular Monolith）** | MVP 阶段不上微服务，按领域模块划分代码，保留未来拆分的边界 |
| 数据库 | **PostgreSQL** | 行程数据强关系（用户-行程-天-行程项），事务一致性重要 |
| 地理查询 | PostgreSQL + **PostGIS** 扩展 | 若未来做"附近推荐/公开行程地理检索"，PostGIS 原生支持地理索引 |
| 缓存 | Redis | 会话、限流 |
| 对象存储 | 腾讯云 COS / 阿里云 OSS | 行程封面图、分享卡片图（打卡照片存储为二期需求） |
| 消息/异步任务 | BullMQ（基于 Redis） | 图片压缩等异步处理；**分享卡片图已确认改为按需同步生成**（见 1.2.4），不占用异步队列 |
| 金额存储 | 整数分（如 `amount_cents`），后端统一用 decimal/整数运算 | 避免浮点数精度问题导致 AA 结算金额对不上 |

### 2.3 关键第三方服务

| 能力 | 服务商 | 说明 |
|---|---|---|
| 登录 | 微信小程序登录（`wx.login` + openid/unionid） | 免用户自建密码体系 |
| 消息推送 | 微信订阅消息 | 行程当天提醒 |
| 内容安全 | 微信内容安全 API（`msgSecCheck` / `imgSecCheck`） | 行程标题/封面图等 UGC 内容过审，合规要求（打卡内容审核为二期需求） |
| 分享 | 微信原生转发 + 服务端生成分享卡片图（Canvas/SSR） | 行程卡片分享到朋友圈；**已确认**点击分享时现场生成（标题+封面图+日期范围，内容尽量简单），不做预生成，见 1.2.4 |
| 邀请加入 | 微信小程序码（`wx.getWXACodeUnlimited`）+ 转发口令 | 生成"加入行程"专属小程序码，同行人扫码/点击即加入 TripMember，无需额外账号体系 |

> **已确认**：地点选择/导航跳转改用微信原生 `wx.chooseLocation` / `wx.openLocation`（见 2.1），MVP 阶段**不再对接腾讯位置服务开发者账号**，此前提到的免费额度限制和 5万元/年商业授权费风险随之消除。若二期要做"地图总览"画路线、算距离这类需要后端地理计算的功能，届时再单独评估是否需要接入腾讯位置服务 WebService API。
>
> 语音识别 ASR（腾讯云/讯飞）**已从 MVP 移除**，改用文字快速记账（见 1.2.2 b）。语音记账挪到二期功能清单，届时再评估 ASR 按量计费的接入成本。

### 2.4 视觉风格 —— 已确认

| 维度 | 方向 | 说明 |
|---|---|---|
| 整体基调 | **轻松活泼，全局统一** | 不因为涉及金钱（AA结算/费用记录页）就切换成收敛严肃的风格——视觉语言全 App 一致，不做"钱的页面单独端着"这种区别对待 |
| 主色调 | **清新自然系** | 建议主色薄荷绿 + 辅助色天蓝，具体色值留给视觉设计阶段微调，这里先定方向，不卡开发进度 |
| 图标风格 | **插画风** | 推荐用开源插画风图标库（如字节 IconPark 的"插画"分类），免费商用、覆盖场景广，不需要额外的定制设计成本——延续"能用免费方案就不新增开支"的原则 |
| 深色模式 | **不做** | 只维护一套配色方案，减少开发和多端适配工作量 |
| 字体 | 小程序系统默认字体，不引入自定义字体包 | 这条是技术约束不是审美取舍：自定义字体包会增加加载体积，容易顶到小程序主包 2MB 的限制（见 5 节非功能性需求） |

> 与 2.1 节的 UI 组件库选型（Taro UI / NutUI）不冲突：不管最终选哪个，都需要在其基础上定制主题色（清新自然系配色）和替换默认图标为插画风，这是组件库通用的主题定制能力，不影响选型本身。

### 2.5 信息架构 —— 已确认

**底部导航栏，两个 Tab**：
- **行程**（默认首页）：展示"我的行程"列表（自己创建的 + 被拉入的），列表顶部有"+ 创建行程"入口；点进某个行程即进入详情页（内含行程项、住宿、AA记账、命运轮盘、分享，见 1.2 各项）
- **我的**：个人信息（头像/昵称）、设置、关于

**不做"发现"Tab**：公开行程广场/内容社区是二期功能（见 1.3），MVP 阶段没有可发现的公开内容，加一个空 Tab 没有意义。

### 2.6 行程详情页布局 —— 已确认

**整页纵向滚动，不做 Tab 切换**：从 Day 1 到最后一天依次往下排布区块，用户一路往下滑看完整个行程，不需要来回点 Tab 切换某一天。

- **页面顶部**：行程总览区（标题、封面图、日期范围、参与人头像一栏），旁边放几个功能入口——记账（AA结算）、命运轮盘、分享。这三个不属于"某一天"的功能统一收在顶部，不散落进每天的区块里
  - **记账入口已确认为常驻输入框**：不是点了才跳转到"费用"专属页面，而是顶部直接放一个"记一笔"输入框/胶囊按钮，点开就能打文字快速记账（如"老王 打车 43"，见 1.2.2 b），减少操作步骤——账记得越顺手，AA 才越"即时"
- **逐天区块**：每个区块顶部是日期标题（如"8月1日 · Day 1"），区块内是当天的 `TripItem` 列表，按 `sort_order` 排列；没填时间的项目归入区块内的"待安排"小节（呼应 1.2.0）
- **住宿卡片的嵌入方式**：住宿覆盖的每一天区块顶部固定展示一个"今晚住 XX 酒店"的小条幅；**连续多天同一家酒店时合并显示**（如"8月1日-8月3日 · 住 XX 酒店"），不是每天重复一整块，保持滚动浏览时的简洁——这是选定"整页滚动"方案后，对 1.2.1 展现方式的进一步细化
- **添加行程项已确认为底部半屏面板**，不跳转整页：点某天区块的"+" → 底部弹出半屏面板 → 面板内点"选地点"触发 `wx.chooseLocation`（微信原生全屏选点，选完自动带回名称/地址/坐标）→ 回到半屏面板，地点已填好，可选填分类（默认按地点类型自动带出）、时间、备注 → 点"添加"，面板收起，当天列表直接多一项。全程不做整页跳转，保持"我在哪一天操作"的上下文不丢失，也配合整页滚动的布局
- **排序手势已确认为长按拖拽**：用小程序原生 `movable-view` 组件实现（免费，平台自带能力，不涉及任何第三方付费服务），长按当天列表里的某一项进入拖拽状态，松手后更新 `sort_order`。相比"编辑模式+上移下移按钮"，长按拖拽更直觉，代价是前端要多花点开发时间处理拖拽浮层跟手、其他项自动让位这些细节——这部分是工程时间成本，不是第三方服务费用
- **每个 `TripItem` 已确认自带"导航"按钮**：点击调用 `wx.openLocation()` 跳转地图 App，指路怎么去。解决"人到了目的地，怎么走到这个点"的真实需求，免费、零额外开发量（呼应 1.2 第2项）

## 3. 系统架构

```
┌──────────────────────┐
│  微信小程序 / H5(Taro)  │
└───────────┬───────────┘
            │ HTTPS (小程序需走微信备案域名)
            ▼
┌──────────────────────┐
│      API 网关/BFF      │  ← 鉴权、限流、聚合裁剪响应
└───────────┬───────────┘
            ▼
┌─────────────────────────────────────────────────────┐
│               后端服务（NestJS 模块化单体）               │
│ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌────────────┐ │
│ │用户模块│ │行程模块│ │POI模块│ │媒体模块│ │费用模块(Expense)│ │
│ └──────┘ └──────┘ └──────┘ └──────┘ └────────────┘ │
└──────┬───────────────┬──────────────┬───────────────┘
       ▼               ▼              ▼
  PostgreSQL         Redis        对象存储(COS)
  (+PostGIS)       (缓存/队列)      (图片/卡片)
  （费用模块的记账/结算数据同样落在 PostgreSQL，依赖事务保证一致性）
            │
            ▼
   第三方服务：微信开放能力（登录/内容安全/小程序码/原生地点选择与导航）
```

> POI 模块的地点数据来自小程序端 `wx.chooseLocation` 选点结果（免费原生能力），后端只做存储和复用，不直接对接腾讯位置服务付费 API（见 2.1、2.3、9）。

**设计原则**：
- MVP 阶段坚持单体，避免过早微服务化带来的运维复杂度
- 模块间通过明确的 Service 接口调用，禁止跨模块直接操作对方数据表 —— 为未来拆分预留边界
- BFF 层做好裁剪聚合，减少小程序端的多次请求（首屏行程详情一次性返回天+行程项+POI 信息）

```
User (用户)
 ├─ id, openid, unionid, nickname, avatar_url, created_at

Trip (行程)
 ├─ id, owner_id(FK User), title, cover_image, start_date, end_date,
 │  destination, status(draft/published), created_at

TripDay (行程日)
 ├─ id, trip_id(FK Trip), date, day_index

TripItem (行程项/一天中的单点安排：景点、餐厅等)
 ├─ id, trip_day_id(FK TripDay), poi_id(FK POI, nullable),
 │  category(景点/餐厅/交通/其他，与Expense.category是独立枚举，不复用),
 │  title, start_time(nullable，未填归入"待安排"), duration_minutes(nullable),
 │  sort_order(拖拽排序，与start_time相互独立、不做冲突校验), note

Accommodation (住宿，挂在 Trip 上而非某一天，跨天区间)
 ├─ id, trip_id(FK Trip), poi_id(FK POI, nullable), name,
 │  check_in_date, check_out_date, note, sort_order

POI (兴趣点，缓存 wx.chooseLocation 选点结果；景点/餐厅/酒店均复用)
 ├─ id, external_id(nullable，微信选点结果一般不带稳定第三方ID), name, category,
 │  location(geography point), address

TripMember (行程成员，用于加入行程 + 参与费用分摊；创建 Trip 时自动为 owner 插入一条)
 ├─ id, trip_id(FK Trip), user_id(FK User, nullable),
 │  display_name(未注册/占位成员可自定义姓名),
 │  claim_token(占位成员专属认领口令，认领后置空；owner自己的记录不需要认领), joined_at

WalletPool (共享钱袋，虚拟记账，不托管真实资金)
 ├─ id, trip_id(FK Trip, unique), balance_cents(=充值总额-池内支出总额), created_at

WalletTopUp (虚拟预充值记录，仅记账数字，不代表真实收款)
 ├─ id, wallet_pool_id(FK WalletPool), member_id(FK TripMember),
 │  amount_cents, created_at

Expense (费用记录，仅支持人民币，不做多币种/汇率；任意 TripMember 可编辑/删除)
 ├─ id, trip_id(FK Trip), payer_id(FK TripMember, nullable，来源为钱袋时为空),
 │  title, amount_cents(人民币分),
 │  category(餐饮/交通/门票/住宿/其他), expense_date,
 │  source(personal垫付 / pool钱袋扣款), split_type(均摊/自定义金额/按比例),
 │  input_method(表单/文字快速记账，语音为二期预留值), created_by(FK TripMember), created_at,
 │  updated_by(FK TripMember, nullable), updated_at(nullable)

ExpenseSplit (费用分摊明细，一条 Expense 对应多条；离团结算通过将某成员的记录标记
              excluded=true 并对剩余成员重新计算 share_amount_cents 实现)
 ├─ id, expense_id(FK Expense), member_id(FK TripMember),
 │  share_amount_cents, excluded(boolean, 默认false)

DecisionSpin (命运轮盘/决策抽签记录，结果由后端生成并落库，不做前端随机)
 ├─ id, trip_id(FK Trip), topic(决策主题，自由文本，如"晚餐吃什么"),
 │  participant_ids(JSON数组，本轮参与的 TripMember id 快照，避免后续成员变动影响历史记录),
 │  selected_member_id(FK TripMember，抽中的人), status(active锁定/voided已作废),

```

> 分享卡片**不建实体表**（已确认，见 1.2.4）：用户点"分享"时后端实时渲染（标题+封面图+日期范围）并上传对象存储，直接返回图片 URL，不做预生成、不落库。

> `CheckIn`（打卡记录，含拍照+定位签到）为二期实体，MVP 数据模型暂不建表，待拍照打卡签到功能启动时再设计。

### 4.1 AA 结算算法（简要）

1. 全程仅人民币，无需汇率换算；按成员汇总净余额：`净余额 = 该成员已垫付总额 + 该成员钱袋充值总额 - 该成员应分摊总额`
   - 净余额 > 0：该成员是"债权人"（该收钱）
   - 净余额 < 0：该成员是"债务人"（该付钱）
   - `source=pool` 的支出不计入某个人的"已垫付"，因为钱已经在充值时记过了，只在计算"应分摊总额"时扣减
2. 用贪心算法做"最少转账笔数"化简：每次取当前欠款最多的人和收款最多的人做一次转账，冲抵后重复，直到所有净余额归零
3. 结算结果只是**建议**（"A 应转给 B 多少钱"），MVP 阶段**不接入真实资金转账**，用户按建议自行微信转账/当面结算——避免直接接入微信支付分账带来的资金托管合规成本
4. 离团结算：将某成员在指定 `Expense` 下的 `ExpenseSplit.excluded` 置为 true，按剩余未剔除成员重新分摊该笔的 `share_amount_cents`，再重新跑一遍第 1-2 步即可得到新结算方案
5. 该算法计算量小，可直接在费用模块的 Service 层同步计算，无需异步任务

## 5. 非功能性需求

| 维度 | 要求 | 落地方式 |
